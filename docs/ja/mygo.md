# Asuka と MyGo

[MyGo](https://mygo.run) を使うと、Go でデスクトップアプリを作れます。スマートフォンへの対応も近日予定です。Asuka では、独自の言語 Asuka でアプリを書き、スマートフォン、デスクトップ、Web 向けに動かします。両者が違うのは、アプリを何で書くか、どこで動くか、そして何より UI を何が表示するかです。MyGo は UI を自前で描画するか、Web ページを表示します。Asuka は各プラットフォーム純正のウィジェットを表示します。

## UI を表示するもの

MyGo のウィンドウが表示するのは、次の二つのどちらかです。

- **MyGo が自前で描画する UI**。GPU（Mac では Metal、Windows では Direct3D 11、ほかに OpenGL）で、MyGo のテーマに沿った見た目に描画します。テキストはシステムのテキストエンジンが担当し、描画した内容からアクセシビリティツリーを組み立てます。
- **Web ページ**。システムの Web ビュー（WKWebView、WebView2、WebKitGTK）で表示し、MyGo が生成する TypeScript クライアントを通じてアプリの Go のコードを呼び出します。

Asuka のアプリは、各プラットフォーム純正のウィジェットを表示します。たとえば `Button` は、iOS では `UIButton`、Android では `MaterialButton`、Mac では `NSButton`、Windows では Windows 11 風に描画された Win32 の `BUTTON`、Linux では `GtkButton`、ブラウザーでは `<button>` になります。一覧は[コンポーネント](components.md)にあります。Asuka は、すべてのプラットフォームに共通のレイアウトエンジンでウィジェットを配置し、プロパティを設定します。描画するのはプラットフォームです。そのため、ウィジェットはプラットフォーム自身のものとして動作します。テキスト入力と自動修正、入力メソッド、スクリーンリーダー、メニュー、スクロール、フォーカスも、すべてプラットフォームのものです。

ここから、次のような違いが生まれます。

- **見た目。** スタイルを何も指定しない Asuka のアプリは、各プラットフォームのアプリと同じ見た目になり、プラットフォームが変われば一緒に変わります（新しい iOS がボタンのスタイルを変えれば、新しい libadwaita がスイッチのスタイルを変えれば、それに従います）。MyGo のウィンドウは MyGo のテーマどおりに、どのシステムでも同じように描画されます。
- **テキスト、入力、アクセシビリティ。** Asuka ではこれらをプラットフォームが担います。MyGo では、自前で描画した内容の上に MyGo が実装します。
- **ウィジェットのないもの。** MyGo はほかの部分と同じように何でも描画できます。Asuka は、対応するウィジェットのないものをプラットフォームの機能で描画します。`Canvas` と `Shape`（[描画](language/drawing.md)を参照）、`std/chart`、`std/svg`、そしてアプリと一緒に各プラットフォームの GPU 向けにコンパイルされるシェーダーです。
- **画面のない環境での画像。** MyGo にはソフトウェアレンダラーがあり、ウィンドウもディスプレイも GPU もなしに、CPU でメモリ上に描画できます。そのため、テストやサーバーがどのマシンでもビューを画像にできます。Asuka のウィジェットはプラットフォームが描画するので、その画像を得るにはプラットフォームが動いている必要があります。デスクトップのウィンドウ（`ASUKA_SNAPSHOT`。Linux のサーバーでは Xvfb）、シミュレーター、エミュレーター、ブラウザーのいずれかです。それがない場合、`asuka test` はアプリのテストブロックをデバイスなしで実行し、画面をテキストで表します。各ビューの種類、位置とサイズ、表示している内容です（[テスト](testing.md)を参照）。

## アプリとは何か

MyGo のアプリは Go のプログラムです。Asuka のアプリは Asuka で書きます（[Asuka 言語](language-tour.md)を参照）。UI のために作られた型付きの言語で、コンポーネントの本体がビューを宣言し、バインディングが状態に追従し、async と await があり、バインディングが何を読み、何がメインスレッドで動くかをコンパイラーが確かめます。開発中は、保存すると数ミリ秒でアプリがリロードされ、状態とビューはそのまま残ります。スマートフォンでも同じです。リリースでは、アプリは事前にコンパイルされます。Asuka のアプリは、ガベージコレクターや二つ目のランタイムを抱えません。プラットフォームの機能が必要なときは、パッケージの Swift、Kotlin、JavaScript、C を通じて使うか、C を直接呼び出します（[Asuka から C を呼び出す](c.md)を参照）。

## 動作する環境

| | MyGo | Asuka |
|---|---|---|
| スマートフォン | 近日対応予定 | iOS と Android |
| デスクトップ | Mac、Windows、Linux | Mac、Windows、Linux |
| ブラウザー | 自前で描画した UI を、WebGL 2 でキャンバスに表示 | ページの DOM。アプリは WebAssembly で動く（[Web](web.md)を参照） |

## ビューの更新

MyGo のビューはアプリの状態の関数で、フレームごとに状態から作り直されます。Asuka のコンポーネントは一度だけ実行されます。ビューを作り、それを自分の状態にバインドします。状態が変わると、それを読んでいるバインディングだけが、そのフレームでまとめて更新されます（[コンセプト](concepts.md)を参照）。

## 使い分け

次のような場合は Asuka を使います。

- アプリが今すぐスマートフォン向けである、またはスマートフォン、デスクトップ、Web を一つのコードで扱いたい場合。
- アプリが各プラットフォームのアプリと同じように見え、同じように動くべき場合。コントロール、テキスト入力、アクセシビリティ、ナビゲーションです。
- あるいは、どのプラットフォームでも同じ独自の見た目を持つべき場合。`std/base` のコンポーネントで作り、中身はプラットフォームのビューのままなので、テキスト入力とアクセシビリティはプラットフォームのものです（[独自の見た目](custom-ui.md)）。

次のような場合は MyGo を使います。

- アプリを Go で書く場合、または Web のフロントエンドを持つデスクトップアプリの場合。既存の Web のコード、HTML と CSS、リッチなドキュメント、ブラウザーにしかないものです。
- 各プラットフォームの見た目ではなく、どのデスクトップでも同じように描画される独自の見た目を持つべき場合。エディター、インスペクター、ゲームなどです。
- 画面のない環境でビューを画像にしたい場合。ピクセルを比べるスナップショットテストや、サーバーで作る画像です。

# ネイティブコード

Asuka がラップしていない機能には、**ネイティブパッケージ**を通じてアクセスします。ネイティブパッケージは、モジュール（`native interface`）やビュー（`native component`）を Asuka で宣言するもので、それを各プラットフォームが自身の言語で実装します。iOS と macOS では Swift、Android では Kotlin、Web では JavaScript、Windows と Linux では C です。`asuka native generate` が、すべての側の型付きのグルーコードを生成します。Asuka からは、モジュールのメソッドをほかのメソッドと同じように呼び出し、ビューを普通のコンポーネントと同じように表示できます。値はコンパクトなバイナリ形式でやり取りされ、JSON もリフレクションも使いません。

```asuka
/// デバイスのバッテリー。
pub native interface Battery {
  /// 充電量で、0 から 1 の値です。
  fn level() -> float
  /// タスクがキャンセルされるまで、充電量が変わるたびに changed を呼びます。
  async fn watch(changed: fn(float))
}
```

```asuka
let battery = try Battery()
let level = try battery.level()
```

```swift
// swift/Battery.swift
final class IOSBattery: Battery {
    func level() throws -> Double {
        UIDevice.current.isBatteryMonitoringEnabled = true
        return Double(UIDevice.current.batteryLevel)
    }
    ...
}
func makeBattery() throws -> any Battery { IOSBattery() }
```

ネイティブパッケージは普通の Asuka パッケージです。アプリの中に置くことも、アプリの依存関係にすることもでき（[パッケージ](packages.md)を参照）、インポートしたアプリにはそのネイティブコードが含まれます。各プラットフォームのコードは、そのプラットフォーム自身のプロジェクト（Swift パッケージ、Gradle モジュール）に置かれ、依存関係もそのプラットフォームのパッケージマネージャー（SwiftPM と Maven）で管理します。

## 必要になるとき

ほとんどのアプリが表示し、使うものは、Asuka のコンポーネント、標準ライブラリ（`std/...`）、プラットフォーム SDK（`platform/...`）でまかなえます。その一覧は [SwiftUI・Expo との比較](parity.md)にあります。まだ何もラップしていないプラットフォームの API、ベンダーの SDK、Asuka にないビュー（地図、グラフ、一つのプラットフォームにしかないコントロール）が必要になったら、ネイティブパッケージを書きます。

パッケージには、それを使うアプリが動くプラットフォームの分だけコードがあれば十分です。コードがないプラットフォームでは、モジュールを作ろうとすると `unsupported` エラーが投げられ、ビューは何も表示しません（ビューがないことがログに出ます）。

C の API を持つライブラリや、どのみち C で書くコードなら、代わりに C を直接呼び出します。`extern fn` は宣言一つで済み、同じ C がすべてのプラットフォームで動きます（Web でも、モジュールにコンパイルされて動きます）。呼び出しで変換するのは型が必要とする分だけで、エンコードは行いません。ネイティブパッケージは、プラットフォーム自身の言語からしか使えないもの（UIKit、Android の API、DOM、ベンダーの Swift や Kotlin の SDK）と、ビューのためのものです。詳しくは [Asuka から C を呼び出す](c.md)を参照してください。

## パッケージの作成

ネイティブパッケージは、ネイティブモジュールを宣言したライブラリ（[パッケージ](packages.md#パッケージの作成)を参照）です。そのため `asuka new` で作ります。

```sh
asuka new --lib --native ./battery          # Asuka、Swift、Kotlin、JavaScript、デスクトップ向けの C
asuka new --lib --native --projects swift,android ./battery
asuka native add web ./battery              # あとからプラットフォームのプロジェクトを追加
```

`asuka new --lib --native` は、すべてのプラットフォームでコンパイルでき、動作するライブラリを生成します。中には、各側で実装済みの `hello` メソッドが入っています。名前を変えて、中身を書いていってください。ネイティブパッケージの構成は次のとおりです。

```
battery/
  asuka.toml               パッケージの名前とバージョン
  battery.asuka            宣言：native interface、native component
  Package.swift            Swift パッケージ（iOS と macOS 向け）
  swift/
    Battery.swift          自分で書く：makeBattery
    Battery.asuka.swift    生成：プロトコル、型、プロバイダー
  android/
    build.gradle.kts       Gradle のライブラリモジュール
    src/main/AndroidManifest.xml          （任意）パーミッション、サービス
    src/main/kotlin/com/example/battery/
      Battery.kt           自分で書く：makeBattery
      Battery.asuka.kt     生成
  web/
    battery.js             自分で書く：export function makeBattery
    battery.asuka.js       生成
    battery.decl.asuka.js  生成：パッケージの列挙型とエラー（あれば）
  desktop/                 Windows と Linux 向けの C
    battery.c              自分で書くもの：battery_make_Battery（_windows.c、_linux.c は一方のプラットフォームだけ）
    battery.asuka.h        生成されるもの：型、vtable、自分で書く関数
    battery.asuka.c        生成されるもの：エンコードとデコード、プロバイダ
  Info.plist               （任意）パッケージが Apple のアプリに求めるもの
  iOS.entitlements         （任意）
  macOS.entitlements       （任意）
```

生成されたファイルは `// Code generated by asuka native. DO NOT EDIT.` で始まり、宣言のハッシュを含んでいます。これらはコミットしてください。

- `asuka dev` と `asuka build` は、ビルドの前に、アプリ自身のネイティブパッケージを生成し直します。そのため、宣言を変更しても、保存すれば反映されます。
- アプリが依存するネイティブパッケージには、生成済みのコードが同梱されています。CLI はそれが宣言と一致するかを確認し、一致しなければ、実行すべきコマンドを示して失敗します。
- `asuka native generate [dir]` で、手動で生成できます。`asuka native check` は古くなったものがあると失敗するので、CI に向いています。

## モジュールの宣言

`native interface` がモジュールになります。

```asuka
/// キッチンのエラー。
pub enum KitchenError: Error {
  /// kitchen: busy
  busy
}

pub enum Level { low, high }

pub struct Item {
  name: string
  weight: float
  level: Level
  tags: [string]
  best: Duration?   // 省略可能
}

pub native interface Kitchen {
  fn name() -> string
  fn items(filter: string) -> [Item]
  async fn cook(recipe: string, progress: fn(float)) -> Item
  fn ask(question: fn(string) -> bool) -> bool
  fn open(name: string) -> Oven
  /// @mainThread
  fn show()
}

/// @mainThread
pub native interface Oven {
  fn heat(to: float, level: Level)
  fn close()
}
```

`Kitchen()` は、プラットフォームの実装を作ります。作成に失敗したときはプラットフォームのエラーを、パッケージにそのプラットフォーム向けのコードがないときは `unsupported` エラーを投げます。プラットフォーム側はいつでも失敗しうるので、どのメソッドもエラーを投げる可能性があり、呼び出しには `try` を付けます。

### 型

| Asuka | Swift | Kotlin | JavaScript | C |
| --- | --- | --- | --- | --- |
| `bool` | `Bool` | `Boolean` | `boolean` | `bool` |
| `int` | `Int` | `Long` | `bigint` | `int64_t` |
| `float` | `Double` | `Double` | `number` | `double` |
| `string` | `String` | `String` | `string` | `char *`（UTF-8、NUL 終端） |
| `bytes` | `Data` | `ByteArray` | `Uint8Array` | `asuka_bytes`（`data`、`len`） |
| `Duration` | `TimeInterval`（秒） | `kotlin.time.Duration` | `number`（ミリ秒） | `int64_t`（ナノ秒） |
| `Decimal`（インポートした std/decimal のもの） | `Decimal` | `java.math.BigDecimal` | `string`。正確なテキスト（`"19.99"`） | `asuka_decimal`（`coefficient`、`exponent`。`asuka_decimal_text`、`asuka_decimal_parse`） |
| `[T]` | `[T]` | `List<T>` | `Array` | `<pkg>_list_T`（`data`、`len`） |
| `[string: T]` | `[String: T]` | `Map<String, T>` | `object` | `<pkg>_map_T`（`keys`、`values`、`len`） |
| `T?` | `T?` | `T?` | `T` または `null` | `T *`（`NULL` は値なし。`string?` は `char *`） |
| `Color` | `Int`（Asuka のエンコーディング）。`AsukaColors.color(_:)` で `UIColor` か `NSColor` になります（セマンティックカラーはライトとダークに追従します） | `Long`。`AsukaModules.color(v, fallback)` で ARGB の `Int` になります | `bigint`。`native.color(v)` で CSS の色になります（セマンティックカラーは CSS 変数） | `uint64_t`。`asuka_desktop_color(v)` で表示中の外観に合わせた RGBA になります |
| パッケージの構造体 | 構造体（自身を含む場合は final class） | data class | オブジェクト | 構造体 `<pkg>_Name` |
| パッケージの列挙型（ケースが値を持たないもの） | ケースごとに static を持つ `RawRepresentable` の構造体 | ケースごとに定数を持つ value class | ケースを収めた凍結（frozen）オブジェクト | ケースごとに定数を持つ `int64_t`（`<pkg>_Level_low`） |
| `native interface`（引数または戻り値） | `any T` | `T` | オブジェクト | `<pkg>_T *` |
| `fn(...)`（引数） | クロージャ | 関数 | 関数 | `<pkg>_fn_…`。その `_call` で呼び出します |
| `Ref`（引数） | `AsukaViewRef`。その `view`（メインアクターで読みます）が Asuka の表示している `UIView` か `NSView`（WebView なら `WKWebView`）で、なければ `nil` | `AsukaViewRef`。その `view`（メインスレッドで読みます）が `View`（WebView なら `WebView`）で、なければ `null` | その要素、または `null` | `uint32_t`（ビューの id）。`asuka_desktop_view(v)` がその `HWND` か `GtkWidget *`、`asuka_desktop_webview(v)` が WebView の `ICoreWebView2 *` か `WebKitWebView *` です |

構造体のフィールドは宣言順に渡されます。構造体の定数とメソッドは Asuka 側に残ります。オブジェクト（ネイティブのインターフェース）を渡せるのは引数か戻り値としてだけで、配列、マップ、構造体の中には入れられません。`Ref` を渡せるのも引数としてだけです。渡るのは呼び出した時点で Ref が持っているビューで（platform/print の `webView(view: Ref, …)` は、`ref:` で入れた WebView のページを印刷します）、プラットフォームのコードはそれをメインスレッドで引きます。Ref がビューを持っていないときや、Asuka がまだそのビューを表示していないときは `nil` になります。それ以外の型を使うと、`asuka native generate` がその位置とともに報告し、代わりに使うべきものを示します。

`Decimal`（`import std/decimal.{Decimal}`）は係数と指数として正確に渡ります。プラットフォーム側から返す値の有効数字が 18 桁を超えるときは、偶数への丸め（銀行型丸め）で 18 桁に丸められます。Asuka はそれ以上の桁を持てないためです。Swift の `Decimal` が表せる指数は -128 から 127 までで、それを超えると NaN になります。

### メソッド

- **エラー**：プラットフォーム側が投げたエラーは、次のいずれかとして返ります。
  - パッケージで宣言したエラー（`: Error` を付けて宣言した列挙型のケースで、その `///` ドキュメントがメッセージになります）。プラットフォーム側では、Swift なら `KitchenError.busy`、Kotlin なら `KitchenException(KitchenError.BUSY)`、JavaScript なら `new KitchenError("busy")`、C なら `asuka_error_declared(err, kitchen_KitchenError_busy)` として投げます。Asuka では `catch KitchenError.busy` で捕まえられます。
  - `AsukaNativeError.unsupported(msg)`、`AsukaUnsupportedException`、`asuka.native.UnsupportedError`、`asuka_error_unsupported`。これらは `unsupported` エラーになります。
  - それ以外のもの。ドメイン（`NSError` のドメインや例外のクラス）、コード、メッセージを持つエラーになります。
- **`async`** を付けたメソッドは非同期になります。Swift では `async`、Kotlin では `suspend`、JavaScript では最初の引数に `AbortSignal` を受け取る `async` 関数、C では `asuka_call` を受け取り、どのスレッドからでも一度だけ応答する関数です。Asuka は、メインスレッドを止めずにその結果を待ちます。タスクがキャンセルされると（それを始めた画面がなくなったときなど）、プラットフォーム側のタスクもキャンセルされます（Swift のタスク、Kotlin のコルーチン、`AbortSignal` の abort、C の `asuka_call_on_cancel`）。ネットワーク、ファイル、ダイアログの応答待ちなど、時間がかかる処理に使ってください。
- **コールバック**：`fn` 型の引数には 2 種類あります。
  - **通知**：何も返さない関数（`progress: fn(float)`）。プラットフォーム側は、呼び出しの実行中でも、呼び出しが戻ったあとでも（ウォッチャーなど）、どのスレッドからでも、何度でも呼べます。Asuka 側ではメインスレッドで実行されるので、状態に書き込めます。
  - **問い合わせ**：何かを返す関数（`question: fn(string) -> bool`）。すぐに実行され、その結果がプラットフォームに返ります。

  コールバックは、それを渡した先のオブジェクトが存在するあいだ有効です。
- **オブジェクト**：メソッドは、ほかのネイティブインターフェースを返せます（`open` は `Oven` を返します）。それぞれがプラットフォーム側では独立したオブジェクトで、Asuka がそれを保持しなくなったとき、または `close()`（`close` という名前の、引数のないメソッド）が呼ばれた時点で解放されます。
- **スレッド**：メソッドはプラットフォーム側で、呼び出したメインスレッドの上で同期的に実行されます。スレッドの切り替えもキューもありません。そのため呼び出しは軽量ですが、時間のかかる呼び出しはメインスレッドを止めてしまいます。そうしたメソッドには `async` を付けてください。
  - メソッドやインターフェースの `///` ドキュメントに `@mainThread` と書くと、必ずプラットフォームのメインスレッドで実行されます。UIKit、AppKit、Android のビューはこれを必要とします。この場合、Swift のプロトコルは `@MainActor` になります。
  - JavaScript はシングルスレッドなので、Web ではこの点は関係ありません。Windows と Linux の C では、すべての呼び出しがメインスレッドで動きます。

## ビューの宣言

`native component` がビューになります。

```asuka
pub native component Segmented(items: [string]) {
  prop selected: int = 0
  event selectedChange(selected: int)
}
```

Asuka からは、普通のコンポーネントと同じように表示できます。

```asuka
state selected = 0

segmented.Segmented(["Day", "Week", "Month"]) {
  bind selected: selected
}
```

- どのプロパティも、読んでいる値に追従します。値が変わったときに、そしてそのときだけ、プラットフォームのセッターがもう一度呼ばれます。
- イベントはメインスレッドで実行されます。
- `bind name: target` は、ビューがプロパティと同じ型のイベント `nameChange(name: T)` で報告するプロパティをバインドします。ユーザーが値を変えたとき（アプリが設定したときではなく）にビューがこのイベントを送り、それが target に書き込まれます。
- ほかの要素と同じスタイルを受け取ります。

各プラットフォームは、ビューをプロトコルとして実装します。プロトコルには、ビュー本体、プロパティごとのセッター、そして作成時に受け取るイベントオブジェクトが含まれます。

```swift
@MainActor final class SwiftSegmented: Segmented {
    let control = UISegmentedControl()
    let events: SegmentedEvents
    var view: AsukaPlatformView { control }          // iOS では UIView、macOS では NSView
    init(_ events: SegmentedEvents) { self.events = events; ... }
    func setItems(_ value: [String]) { ... }
    func setSelected(_ value: Int) { ... }
    // 変更時：events.selectedChange(selected: i)
}
@MainActor func makeSegmented(_ events: SegmentedEvents) -> any Segmented { SwiftSegmented(events) }
```

プロパティが届く順番は決まっていません。そのため、二つのプロパティに依存するビュー（項目の中から一つを選ぶものなど）は、受け取った値を保持しておき、両方が揃ってから反映します。Asuka は、自前のビューと同じ方法でこのビューのサイズを決めます。

- Swift では `sizeThatFits`（iOS）または `fittingSize`（macOS）。ビューが `AsukaSizing` に準拠していれば、その `sizeThatFits`
- Android では、ビュー自身の計測
- JavaScript では `measure(c)`
- C では vtable の `measure`。なければウィジェット自身のサイズ（後述）

固有のサイズを持たないビューは、スタイルからサイズを決めます。解放すべきものを持つビューは、`AsukaDestroying` に準拠させるか、JavaScript か C の vtable に `destroy` を持たせます。

`examples/media/segmented` は、すべてのプラットフォームで動く完全なビューの例です。

アプリのテスト（`asuka test`。プラットフォームのコードはありません）では、ネイティブビューはコンポーネント名で表示され、`app.tap("Segmented")` はプラットフォームのボタンと同じように `press` イベントを送ります。

## アプリに必要なもの

パッケージがアプリに求めるもの（権限、利用目的の説明、バックグラウンドモード、entitlement）はパッケージ自身が宣言し、それを使うアプリだけに付きます。宣言はパッケージの `asuka.toml` に書きます。次の表は、パッケージをインポートするすべてのアプリに適用されます：

```toml
[ios]
usage = { NSLocationWhenInUseUsageDescription = "To show where you are." }
backgroundModes = ["audio"]
entitlements = { aps-environment = "development" }   # シミュレータ向けビルドの値
plist = { LSApplicationQueriesSchemes = ["mailto"] } # true、文字列、またはアプリのものと合わせる配列

[android]
permissions = ["android.permission.ACCESS_FINE_LOCATION", "android.permission.WRITE_EXTERNAL_STORAGE:28"]
application = ['<service android:name="com.example.battery.Watcher" android:exported="false" />']
manifest = ['<queries><intent><action android:name="android.intent.action.TTS_SERVICE" /></intent></queries>']
```

権限を `"name:28"` と書くとその API レベルまで、`"name|neverForLocation"` と書くとその `usesPermissionFlags` 付きになります。利用目的の説明は、アプリ自身の `asuka.toml` のものがパッケージのものより優先されます。

パッケージの一部だけが必要とするものは、同じキーで `[uses.<member>]` の表に書きます。アプリのコード（または依存パッケージのコード）がそのメンバー（関数、型、store。型のメソッドやフィールドは `"Type.name"`。フィールドは、コードが構造体をそのフィールド付きで作るか、代入するか、読むときに数え、既定値のままなら数えません）を参照したときだけ、アプリに付きます。同じ名前のローカル関数や、テストブロックの中の参照は数えません。platform/location のバックグラウンド部分はこう宣言しています：

```toml
[uses.requestAlways.android]
permissions = ["android.permission.ACCESS_BACKGROUND_LOCATION"]

[uses.startUpdates.ios]
backgroundModes = ["location"]
```

パッケージのコードの横にあるファイル（Gradle モジュールの `AndroidManifest.xml`、Swift パッケージの `Info.plist` と entitlements。後述）は、パッケージをインポートするすべてのアプリに適用されます。そのパッケージを使うどのアプリにも必要なものはそこに、あるメンバーだけが必要とするものは `[uses]` に書きます。

## iOS と macOS：Swift

パッケージの Swift のコードは、Swift パッケージとして書きます。パッケージのルートに `Package.swift` を置き、ソースは `swift/` に入れます。一つのパッケージで iOS と macOS の両方に対応し、両者で異なる部分には `#if canImport(UIKit)` を使います。

```swift
// swift-tools-version:5.9
import PackageDescription

let package = Package(
    name: "BatteryNative",
    platforms: [.iOS("16.0"), .macOS("11.0")],
    products: [.library(name: "BatteryNative", targets: ["BatteryNative"])],
    dependencies: [
        .package(url: "https://github.com/egoist/asuka", from: "0.1.0"),
        .package(url: "https://github.com/firebase/firebase-ios-sdk", from: "11.0.0"),
    ],
    targets: [
        .target(name: "BatteryNative", dependencies: [
            .product(name: "Asuka", package: "asuka"),
            .product(name: "FirebaseAnalytics", package: "firebase-ios-sdk"),
        ], path: "swift"),
    ]
)
```

このパッケージは自分のもので、自由に書けます。依存関係、ターゲット、リソース、C ターゲット、バイナリターゲットは、ほかのパッケージと同じく SwiftPM の仕組みそのものです。Asuka はこれをアプリやほかのネイティブパッケージとまとめてビルドし、アプリにリンクして（静的なバイナリフレームワークは、ベンダーの SDK が前提とするとおり丸ごとリンクします）、生成された動的フレームワークとリソースバンドルを埋め込みます。`asuka`（プロダクト `Asuka`）は、生成コードが土台にするライブラリです。ビルドには手元の `asuka` に付属するものが使われるので、常にアプリの Asuka と一致します。パッケージが宣言する `platforms` も考慮されます。それより古い iOS や macOS 向けにアプリをビルドすると、パッケージが必要とするバージョンを示して失敗します。また、どちらか一方だけを挙げたパッケージ（`platforms: [.iOS("16.0")]`）は、そのプラットフォーム向けにだけビルドされます。Apple TV のビルドに入るのは、tvOS（`.tvOS("17.0")`）を挙げたパッケージだけです。[テレビ](tv.md#tvos-のネイティブパッケージ)を参照してください。Apple Watch のビルドに入るのは watchOS（`.watchOS("10.0")`）を挙げたパッケージだけで、そのビューは SwiftUI のものです。[Apple Watch](watch.md#watchos-のネイティブパッケージ) を参照してください。

Xcode で編集するには、`Package.swift` を開きます。Xcode は `asuka` をその URL から解決するので、生成コードも自分のコードも、ビルド時と同じように型チェックされます。

自分で書く Swift では、インターフェースごと、ビューごとに関数を一つずつ用意します。必要な関数は、生成されたファイルの先頭に列挙されています。

```swift
func makeKitchen() throws -> any Kitchen
@MainActor func makeOven() throws -> any Oven      // @mainThread のインターフェース
@MainActor func makeDial(_ events: DialEvents) -> any Dial
```

プラットフォーム側で作って Asuka に渡すオブジェクト（`open` が返す `Oven`）も、自分のコードで作ります。バックグラウンドで動くメソッドからメインアクターのオブジェクトを作るには、`try AsukaNative.onMain { SwiftOven() }` を使います。

`Package.swift` の隣に置いた `Info.plist` には、パッケージが Apple のアプリに求めるものを書きます。

- 利用目的の説明文（`NSBluetoothAlwaysUsageDescription`）。アプリ自身の `asuka.toml` にある説明文が優先されます。
- 配列（`UIBackgroundModes`）。アプリやほかのパッケージの配列と結合されます。
- そのほかのキー。アプリが設定していなければ、その値が設定されます。

エンタイトルメントは `iOS.entitlements` と `macOS.entitlements` に書きます。プロビジョニングプロファイルにそのエンタイトルメントがないと、署名付きのビルドは失敗し、それを要求したパッケージの名前が示されます。

## Android：Kotlin

パッケージの Kotlin のコードは、`android/` にある Gradle のライブラリモジュールです。

```kotlin
// android/build.gradle.kts
plugins {
    id("com.android.library")
    id("org.jetbrains.kotlin.android")
}

android {
    namespace = "com.example.battery"
}

dependencies {
    implementation("com.google.code.gson:gson:2.11.0")
}
```

Kotlin のコードは、`src/main/kotlin/` の下の、生成されたファイルが指定するパッケージに置きます。パッケージ名は、パッケージの名前（asuka.toml の `name`）の各部分を小文字にし、ホスト部分を逆順にして先頭に置いたものです（`@acme/battery` なら `_acme.battery`、`github.com/you/battery` なら `com.github.you.battery`）。CLI はこのモジュールをアプリの Gradle ビルドに組み込み、そのビルドが次の設定を行います。そのため、モジュールに書く必要があるのは namespace と依存関係だけです。

- SDK レベル、Java 17、Kotlin のツールチェーン
- Asuka の Android ライブラリ（`dev.asuka`）への依存。これにより AndroidX、Material Components、コルーチンも入ります。

モジュールの `src/main/AndroidManifest.xml`（パーミッション、サービス、レシーバー、プロバイダー）は、ほかのライブラリと同じように、アプリのマニフェストにマージされます。

```kotlin
private class AndroidBattery(private val context: Context) : Battery {
    override fun level(): Double { ... }
    override suspend fun watch(changed: (Double) -> kotlin.Unit) { ... }
}
fun makeBattery(): Battery = AndroidBattery(AsukaModules.context)
```

`AsukaModules.context` はアプリケーションのコンテキストで、どのスレッドからでも使えます。`AsukaModules.activity` は、アプリを表示しているアクティビティがあればそのアクティビティで、ダイアログや権限のリクエストなど、アクティビティが必要な処理のためにメインスレッドで使います。ビューのイベントオブジェクトは、そのビューが作られたテーマ付きのコンテキストを持っています（`events.context`）。`AsukaModules.onMain { }` は、Swift の `AsukaNative.onMain` と同じく、メインスレッドでオブジェクトを作ります。生成コードでは Kotlin の `Unit` を `kotlin.Unit` と書くので、自分のコードに `Unit` という名前の型があっても問題ありません。

補完を使ってモジュールを編集するには、アプリの Android プロジェクト（`asuka build --platform android` が書き出します）を Android Studio で開きます。モジュールは、その中に `:native-<package>` として含まれています。

## Web：JavaScript

パッケージの JavaScript のコードは `web/<package>.js` です。これは ES モジュールで、生成された `web/<package>.asuka.js` がインポートする関数をエクスポートします。

```js
export function makeBattery() {
  return {
    async level() { return (await navigator.getBattery()).level; },
    async watch(signal, changed) { ... },
  };
}

export function makeSegmented(events) {
  const el = document.createElement("div");
  return { el, setItems(v) { ... }, setSelected(v) { ... }, measure: () => [216, 32] };
}
```

メソッドは Promise を返してもかまいません。Asuka で `async` でないメソッドでも同じです。パッケージで宣言したエラーは、生成されたクラスで投げます（`import { KitchenError } from "./kitchen.asuka.js"`）。パッケージの列挙型とエラーはパッケージ自身のモジュールが実行される前に作られるので、モジュールの読み込み時に参照してもかまいません（列挙型のケースの表を作るなど）。パッケージが宣言していない名前をインポートすると、`asuka native generate` がエラーにします。`web/` 内のファイルはすべてアプリに同梱されるので、モジュールは自前のヘルパーをインポートしたり、`import.meta.url` からの相対パスでアセットを取得したりできます。`asuka dev --platform web` では、ファイルが変わるとページがリロードされます。詳しくは [Web](web.md#ネイティブコード) を参照してください。

## Windows と Linux：C

Windows と Linux でのパッケージのコードは C で、パッケージの `desktop/` ディレクトリに置きます。アプリの実行ファイルへコンパイルされます（ほかのシステムからビルドするときは Zig を使います）。名前が `_windows.c` か `_linux.c` で終わるファイルはそのプラットフォームでだけビルドされ、それ以外は両方でビルドされます。違いのある箇所は `#ifdef _WIN32` で分けます。あるプラットフォーム向けのファイルがパッケージに一つもなければ、そこにはパッケージのコードがなく、モジュールを作ると `unsupported` が投げられます。`asuka native generate` は、自分のコードがインクルードする `<package>.asuka.h` を生成します。パッケージの型、インターフェースごとの vtable、そして自分で書く関数（インターフェースとビューごとに一つずつ）が書かれています。

```c
// desktop/battery.c
#include "battery.asuka.h"

#include <stdlib.h>
#ifdef _WIN32
#include <windows.h>
#else
#include <stdio.h>
#include <time.h>
#endif

// level_now はバッテリーの残量で、0 から 1（負の値はバッテリーなし）。
static double level_now(void) {
#ifdef _WIN32
	SYSTEM_POWER_STATUS s;
	return GetSystemPowerStatus(&s) && s.BatteryLifePercent <= 100 ? s.BatteryLifePercent / 100.0 : -1;
#else
	FILE *f = fopen("/sys/class/power_supply/BAT0/capacity", "r");
	int n = -100;
	if (f) {
		if (fscanf(f, "%d", &n) != 1) n = -100;
		fclose(f);
	}
	return n / 100.0;
#endif
}

static double level(battery_Battery *self, asuka_error *err) {
	double l = level_now();
	if (l < 0) asuka_error_unsupported(err, "no battery");
	return l;
}

typedef struct {
	battery_fn_float changed;
	asuka_call *call;
} watching;

// run は専用のスレッドで残量を毎秒読み、監視しているタスクがキャンセルされるまで続けます。
static void run(void *p) {
	watching *w = p;
	double last = -2;
	while (!asuka_call_cancelled(w->call)) {
		double l = level_now();
		if (l != last) battery_fn_float_call(w->changed, l);  // メインスレッドに投げられます
		last = l;
#ifdef _WIN32
		Sleep(1000);
#else
		nanosleep(&(struct timespec){1, 0}, NULL);
#endif
	}
	asuka_error e = {0};
	asuka_error_cancelled(&e);
	asuka_call_fail(w->call, &e);
	free(w);
}

static void watch(battery_Battery *self, battery_fn_float changed, asuka_call *call) {
	watching *w = malloc(sizeof *w);
	*w = (watching){changed, call};
	asuka_desktop_spawn(run, w);
}

static const battery_Battery_vtable vt = {.level = level, .watch = watch};

battery_Battery *battery_make_Battery(asuka_error *err) {
	battery_Battery *b = malloc(sizeof *b);
	b->vt = &vt;
	return b;  // Asuka が手放すと解放されます（vtable に release がないため）
}
```

- **呼び出し**は、プラットフォームの UI があるメインスレッドで動きます。同期メソッドは結果をそのまま返し、メインスレッドを止めてはいけません。失敗したメソッドは `err` を設定してゼロ値を返します。`async` のメソッドは `asuka_call` を受け取ってすぐに戻り、あとでどのスレッドからでも、生成された `_done`（`battery_Battery_watch_done`）か `asuka_call_fail` で一度だけ応答します。呼び出したタスクがなくなったことは `asuka_call_cancelled` と `asuka_call_on_cancel` でわかります。`asuka_call_off_cancel` で登録したキャンセル処理を外せば、呼び出しが応答する前にそのコンテキストを解放できます。ブロックする処理は `asuka_desktop_spawn` で専用のスレッドに回します。
- **メモリ**：境界を越える値はすべて `malloc` で確保します。メソッドの引数は生成されたコードのもので、同期呼び出しのあいだと、非同期呼び出しが応答するまで有効です（それより長く使うならコピーします）。メソッドが返す（または応答する）値は生成されたコードに渡り、そちらで解放されます（リテラルは `asuka_strdup` してから返します）。コールバックの引数は自分のもののままで、問い合わせ型のコールバックが返した値は自分で解放します（`<pkg>_<Type>_free`）。vtable の `release` が `NULL` なら、Asuka が手放したときにオブジェクトがそのまま解放されます。
- **コールバック**は `<pkg>_fn_…_call` で呼び出します。通知型はどのスレッドからでも呼べます（メインスレッドに投げられます）。問い合わせ型はメインスレッドならその場で動き、ほかのスレッドからは結果を待ちます。
- **ビュー**：`<pkg>_make_<View>(events)` が、ビューのオブジェクトとその `widget`（`HWND`（`events.parent` の子）か `GtkWidget *`）を作ります。Asuka がそれを表示し、ビューがなくなるときに破棄します。プロパティごとに vtable のセッター（`set_selected`）があり、ウィジェットが自分のサイズを返せないときは `measure` がサイズを決めます。イベントは生成された関数（`segmented_Segmented_selectedChange(events, i)`）で、どのスレッドからでも呼べます。
- **Asuka の C API**：`asuka_desktop.h` は、デスクトップでパッケージの C が使える Asuka の機能です。メインスレッドへの投げ込み、ビューのあるウィンドウ、アプリの名前・ID・バージョン・ディレクトリ、アセット、表示中の外観に合わせた色、HTTP（`asuka_fetch`。レスポンスを少しずつ受け取るとき、ダウンロードをそのままファイルに書くときは `asuka_fetch_stream`、どのスレッドからでもリクエストを止めるときは `asuka_abort`）、アプリが指定したファイル（`asuka_desktop_local_file`）があります。`asuka_windows.h` には COM と WinRT の補助（UTF-16、vtable のスロット、HSTRING、アクティベーションファクトリ、デリゲート、非同期操作の待機、WIC の画像、システムウィンドウが受け取るブロードキャスト）があります。`asuka_barcode.h` は画像のグレースケールから QR コードやバーコードを読み取り、どのデスクトップでも使えます。`asuka_linux.h` は、パッケージが使う GLib、GIO、GTK、libadwaita の関数を宣言して、実行時に解決します（`G(g_variant_new)(…)` のように呼びます）。そのため、ビルドに GTK のヘッダーは要りません。
- **ライブラリ**：パッケージの C が各プラットフォームでリンクするものは、その `asuka.toml` に書きます。

  ```toml
  [windows]
  libraries = ["ole32", "winhttp"]
  [linux]
  libraries = []
  ```
- **Flatpak にないシステムのライブラリ**：パッケージの Linux の C が実行時に開く（`asuka_linux_load`）ライブラリのうち、GNOME ランタイムにないものは、パッケージのモジュールが Flatpak にビルドします。`linux.flatpakModules` に、マニフェストのモジュールを一つずつ YAML で（`name:` の行から）書き、アプリより先にビルドされます（platform/pdf は Poppler をこうしてビルドします）。
- **ディストリビューションのパッケージが必要とするシステムのライブラリ**：パッケージの Linux の C が開くライブラリは、アプリの `.deb` や `.rpm` が依存するパッケージになり、パッケージマネージャーがあわせてインストールします。パッケージの `linux.deb` と `linux.rpm` に、Debian と Fedora それぞれの書式でパッケージ名を書きます（`"libpoppler-glib8t64 | libpoppler-glib8"`、`"poppler-glib"`）。あるとよいもの（コーデックやモデル）は `linux.debRecommends` と `linux.rpmRecommends` に書きます。

  ```toml
  [linux]
  deb = ["libshumate-1.0-1"]
  rpm = ["libshumate"]
  ```
- **パッケージ自身のライブラリ**：パッケージがビルドに使う C のライブラリ（パーサー、デコーダー）は、手を加えずに `desktop/third_party/<名前>/` に置き、ライセンスとバージョンを添えます。パッケージ自身のファイルがそのソースを取り込む（`#include "third_party/<名前>/<名前>.c"`）ので、パッケージの C と一緒にコンパイルされ、変更すればアプリもビルドし直されます。

macOS では、パッケージの Swift（`Package.swift`）が動き、C は動きません。

## ネイティブコードの開発

- **iOS と Android**：`asuka dev` は、ネイティブパッケージを含むアプリの外側をビルドしてインストールし、ネイティブコードが変わったときにビルドし直します。Swift、Kotlin、`Package.swift`、`build.gradle.kts`、`Info.plist`、マニフェストの変更も対象です。アプリの Asuka のコードは、保存するとビルドし直さずにリロードされます。ネイティブパッケージを持たないアプリは、ホットリロードモードで開発用アプリの中で実行されます。開発用アプリに入っているのは、Asuka 自身のネイティブコードだけです。[開発](development.md#開発用アプリ)を参照してください。
- **macOS**：パッケージの Swift は、アプリの Swift ライブラリにビルドされます。こちらも変更があったときだけビルドされ、アプリは状態を保ったまま再実行されます。
- **Windows と Linux**：パッケージの C は、アプリの実行ファイルにビルドされます。こちらも変更があったときだけです。
- **Web**：パッケージの JavaScript が変わると、ページがリロードされます。

iOS や macOS でパッケージを初めてビルドするときに Swift の依存関係を解決し、以降のビルドではそれを再利用します。

## 制限

- `asuka build --platform ios --xcframework`（自分の Xcode プロジェクトにアプリを埋め込む場合）は、Swift を含むネイティブパッケージを受け付けません。代わりに、それらの Swift パッケージをそのプロジェクトに追加してください。
- `asuka build --platform android --aar` には、ネイティブパッケージのモジュールは含まれません。埋め込み先の Gradle プロジェクトに追加してください。
- ディレクトリ名が同じネイティブパッケージが二つあると、両方に Swift を持たせることはできません。SwiftPM は、ローカルパッケージをディレクトリ名で識別するためです。

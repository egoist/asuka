# 0015: Diagnostics with codes, for people and agents

- **Status**: Draft
- **Created**: 2026-11-18
- **Related**: 0005 (devtools), 0012, 0013, 0014, lang/check
  (`errorf`, `warnf`, `Diagnostic`), lang/lsp, core/src/signal
  (`AK_MAX_PASSES`), `asuka dev`'s logs; Solid 2.0 ("The Long Hold":
  diagnostics with stable codes, a fix link and an agent repair guide),
  ReactiveScript's rule IDs, `rustc --explain`, clippy's lint names

## Summary

Asuka's compiler errors are good sentences: most say what's wrong and
what to write instead. But they're only sentences. Nothing names them,
so an editor can't link one, a test can't expect one, an agent can't
look one up, and the same mistake worded two ways in two places reads
as two mistakes. Run-time problems are worse off: an effect that loops
panics with "effects still dirty after 100 passes (an infinite loop?),
e.g. effect text", naming neither the effect nor its line, and what the
reactive graph could tell the developer (a load that waited for another
for no reason, a write that ran ten thousand bindings, a screen that's
been showing old data for seconds with no sign) it doesn't say at all.

Solid 2.0 made this a headline: development builds report each reactive
mistake with a stable code, the source location and a link to the fix,
and ship a repair guide for agents next to the library. This RFC does
the same for Asuka:

1. **Every diagnostic has a code**: a stable kebab-case name,
   `error[write-in-binding]`, from one table that also holds its
   explanation, its fix and two examples, a wrong one and a right one,
   which a test compiles.
2. **The table is the documentation**: `asuka explain write-in-binding`
   prints it, `asuka.dev/docs/errors/write-in-binding` shows it, in
   English, Chinese and Japanese, generated from the table.
3. **Every tool says the same thing**: the terminal, `asuka check
   --json`, the language server (`code` and `codeDescription`), `asuka
   test` and `asuka dev`.
4. **Run-time diagnostics from the graph**, in development builds:
   effect loops with their line, loads that wait for each other
   needlessly (waterfalls), holds that last with nothing saying so, and
   writes that fan out too wide, each with a code from the same table.
5. **An agent guide in every project**: `asuka new` writes an
   `AGENTS.md` that says how to check, test and look up a code, and
   `asuka guide` prints the language on one page for the version
   installed.

## Motivation

- **Codes are what tools hold on to.** TypeScript's `TS2345`, Rust's
  `E0499` and clippy's `needless_borrow` are searchable, linkable,
  suppressible by name and testable. A sentence that's reworded breaks
  every test that matched it; a code survives.
- **The explanation doesn't fit in the message.** "can't assign to
  count here: what the UI follows is computed, not changed; change state
  in a handler (on press { … }), a fn, a task or an effect" is already
  long, and still doesn't say why, or show the right program. A page per
  code can.
- **Agents write a growing share of the code.** They fix what they can
  look up. ReactiveScript measured it: fresh agents given its spec,
  whose errors cite numbered rules, predicted 70 of 71 frames of the
  apps they wrote. Solid ships a `SKILL.md` in `node_modules` for the
  same reason. An Asuka project carries nothing an agent can read, and
  the language is new to every model.
- **The graph knows more than it says.** The core sees every read,
  write and run. Today it uses that to schedule, and once, after a
  hundred passes, to panic. The mistakes it could name are the ones that
  cost the most and show the least: a waterfall shows as a slow screen,
  a wide fan-out as a dropped frame, a long hold as a user looking at
  stale data.

Today there are 540 `errorf` calls in lang/check and 2 `warnf`s; the
run time has one reactive diagnostic, the panic.

## Decisions

| Question | Decision | Why |
|---|---|---|
| What a code is | A kebab-case name (`write-in-binding`, `missing-await`, `row-without-key`), never reused or renamed once released | Names read as what they mean, in a terminal and in a prompt; clippy's and Solid's choice. Numbers need a lookup to mean anything. |
| What gets one | Every error and warning, compile time and run time | A code is cheapest when it's universal: tools and tests can rely on its being there. |
| Granularity | One per rule, not per message: the 540 calls share codes where they enforce the same rule | The page explains the rule; the message says where it was broken. |
| Where they live | One table, `lang/diag`: code, severity, a one-line summary, the explanation, the fix, a wrong and a right example, and their Chinese and Japanese | One source, generated outputs, as the wire, the bytecode and the elements are. |
| The docs | `docs/errors/<code>.md` and its zh and ja pages, generated by `go generate ./lang/diag`, committed | The site and the CLI show the same text, for the same version. |
| Offline | `asuka explain <code>` prints the page, in the language `LANG` asks for | `rustc --explain`. Version-matched, no network. |
| The format | `file:line:col: error[code]: message`, then `  = help: …` when there's a fix, then `  = see https://asuka.dev/docs/errors/code` | Rust's shape, which editors and agents already parse. |
| Machine-readable | `asuka check --json` and `asuka test --json`: one JSON object per line (code, severity, file, range, message, help, url); the language server sets `code` and `codeDescription.href` | LSP 3.16's fields; JSON lines stream. |
| Run-time diagnostics | Development builds only (the player, `asuka run`, `asuka test`): detectors in the core, off in release builds | Their bookkeeping isn't free; a release build pays nothing. |
| Run-time locations | Every effect, memo, binding and loader carries its Asuka source position (its `ak_comp_info` label) | The VM already knows lines (`ak_vm_traceback`); the graph's nodes should too. |
| Release crashes | A panic keeps its code in a release build, so a crash report says which | Codes cost a string, and crash reporting groups by them. |
| Thresholds | Counted, not timed, except the hold, which is time the user waits | Tests count work (AGENTS.md); `asuka test`'s clock is virtual, so the hold's test still doesn't wait. |
| The agent guide | `AGENTS.md` written by `asuka new`, short, pointing at `asuka guide` and `asuka explain`; `asuka guide` prints the language and the workflow on one page, generated from docs/language | `AGENTS.md` is the convention coding agents read; the guide comes from the CLI so it matches the compiler that will check the code. |

## Compile-time codes

The checker's `errorf(n, format, args...)` becomes `errorf(n, code,
format, args...)`, and `Diagnostic` gets `Code`. The table:

```go
// lang/diag/codes.go
var WriteInBinding = def(Code{
	Name:     "write-in-binding",
	Severity: Error,
	Summary:  "state written where the UI follows it",
	Why: `A binding, a let and a component's body say what stays true;
they run again whenever what they read changes. A write there would run
on every change it causes.`,
	Fix: `Write state in a handler (on press { … }), a fn, a task or an
effect. A value computed from state is a let.`,
	Wrong: "component C {\n  state n = 0\n  Text(\"{n += 1}\")\n}",
	Right: "component C {\n  state n = 0\n  Button(\"{n}\") { on press { n += 1 } }\n}",
})
```

with `codes_zh.go` and `codes_ja.go` beside it holding the translated
`Summary`, `Why` and `Fix`, written as natural Chinese and Japanese per
docs/zh/TRANSLATING.md and docs/ja/TRANSLATING.md.

`go test ./lang/diag` checks, for every code: the wrong example fails to
compile with exactly that code, the right one compiles (both checked for
every platform, as `asuka check` does), all three languages are there,
and the generated pages are current. `go test ./lang/check` checks that
no diagnostic is reported without a code.

The terminal:

```
app.asuka:14:9: error[write-in-binding]: can't assign to count here
  = help: change state in a handler (on press { … }), a fn, a task or an effect
  = see https://asuka.dev/docs/errors/write-in-binding
```

The message keeps saying where and what; the help line is the fix the
message has today, split out so tools can show it as a quick fix; the
link is the page.

The first codes, from the rules the earlier RFCs add:
`snapshot-state` (0012: a reactive initializer read once is `peek`),
`effect-writes-what-it-follows` (0012), `row-without-key` (0012),
`peek-untracked` (0012: `peek` where nothing is followed), and from
today's checker, among others: `write-in-binding`, `statement-in-view`,
`missing-await`, `missing-try`, `async-in-effect`, `prop-not-assignable`,
`not-pub`, `spawn-captures-state`, `closure-keeps-itself`.

## Run-time diagnostics

The core reports them through one function,

```c
// ak_diag reports a run-time diagnostic: its code, the source positions
// it concerns (each an ak_comp_info label: "Picker's effect at
// picker.asuka:12"), and a message. In a release build only panics
// reach it, and it adds their code to the panic.
void ak_diag(const char *code, const char *msg, const char *const *where, int nwhere);
```

which the player sends to `asuka dev` on the channel its logs use, and
`asuka test` and `asuka run` print. Each detector is behind
`ak_diag_enabled`, set by the development hosts and the fake host; off,
it's one predictable branch at most, outside the per-node loops.

| Code | When | Says |
|---|---|---|
| `effect-loop` | An effect is still dirty after `AK_MAX_PASSES` (today's panic) | Which effect, its line, and the state it wrote last. Compile time catches what it can see (0012). |
| `load-waterfall` | A load starts in content that appeared because another load answered, and its arguments don't read that load | Both loads' lines: "Posts's load waited for Profile's, but doesn't use it: start it beside it, and pass the result down". The second load could have run at the same time. |
| `long-hold` | A load has been holding old content (0014) for more than 2 seconds since its arguments changed, and nothing on screen reads its `loading` | "Profile has shown the last user for 2 s while loading the next, with nothing saying so: read user.loading". Solid 2.0's "long hold". |
| `wide-fanout` | One write runs more than 1,000 bindings and memos in a flush, more than once | The state, the line of the write, and the lines of the bindings run most: per-path reads (0013) or a set's `contains` follow less. |
| `effect-in-effect-pass` | An effect's write makes a binding run twice in one flush | The effect and the state: a `let` or a following state (0012) settles in one pass. |

They're reported once per site per run of the app, so a list doesn't
print the same thing ten thousand times.

The counting the detectors need (runs per flush per node, which loader
caused a branch) is kept only when `ak_diag_enabled`; the steady-state
allocation tests run with it on and off.

## Locations

Each `ak_comp_info` the lowering makes gets a label with the component
and the source line: `"Picker's effect at picker.asuka:12"`, `"Card's
text binding at card.asuka:30"`, `"load at profile.asuka:8"`. The
lowering already makes one per kind of node; it becomes one per site,
static and frozen, so nothing is allocated per node. Panics, the graph's
diagnostics and 0005's inspector all read it.

## For agents

`asuka new` writes, beside `asuka.toml` and `app.asuka`:

```markdown
# AGENTS.md

This is an Asuka app (https://asuka.dev). Before writing Asuka, read the
language for the installed version: `asuka guide`.

- Check: `asuka check --json` (one diagnostic per line, each with a code)
- Look up a code: `asuka explain <code>`
- Test: `asuka test --json`; run: `asuka dev`
- A component's body is declarations; state is written in handlers,
  fns, tasks and effects. Lists in views need `key`.
```

`asuka guide` prints, for the CLI's version:

- the language on one page (docs/language-tour.md and docs/language,
  joined);
- the workflow above;
- every code's summary and fix, one line each.

It's generated at build time from the docs and the table, embedded in
the CLI, and checked current by a test. A project that keeps its own
`AGENTS.md` keeps it: `asuka new` writes one only in a new directory.

## Measuring it

ReactiveScript measures whether its rules are learnable: fresh agents,
given only the spec, write apps cold, and the apps' behavior is checked.
Asuka gets the same, by hand, not in CI (it needs a model and costs
money):

- `eval/tasks/`: a dozen small apps (a todo list, a search with
  results, a settings screen, a profile that loads), each a prompt and
  an `asuka test` file that checks the app's behavior on the fake host.
- `go run ./eval -agent <command>`: runs the agent in a fresh project
  made by `asuka new`, with nothing but `AGENTS.md`, lets it use `asuka
  check`, `asuka explain` and `asuka test`, and records whether the
  tests pass, how many compiler round trips it took and which codes it
  hit.

The codes agents hit most, and the ones they fail to fix, are where the
messages, the pages and the guide need work.

## Alternatives

- **Numbers** (`A0423`). Stable and short, but meaningless without a
  lookup, in a terminal or a prompt.
- **Codes only for the reactive rules** (Solid's scope). A tool that
  can rely on every diagnostic having a code is simpler than one that
  can't; the work is one table.
- **Docs pages written by hand.** They drift from the compiler; the
  examples in the table are compiled, the pages generated.
- **Run-time detectors in release builds.** The counting isn't free,
  and release users can't act on them; crash reports carry panics'
  codes instead.
- **A `SKILL.md` per agent product.** Each tool reads its own place;
  `AGENTS.md` is the one they share, and `asuka guide` keeps the long
  part in the CLI, where it can't go stale.

## Milestones

1. **The table and the format.** `lang/diag`, `Diagnostic.Code`, the
   terminal format, `--json` for `check` and `test`, the language
   server's `code` and `codeDescription`; the codes for the checker's
   reactive rules first, with their pages.
2. **Every compile-time diagnostic coded.** The rest of the 540, grouped
   by rule; the test that none is uncoded.
3. **`asuka explain`, the generated pages** in three languages, the
   site's `/docs/errors`.
4. **Locations in the graph.** Labels per site, `ak_diag`, the
   `effect-loop` panic with its line and state.
5. **The detectors.** `load-waterfall`, `long-hold`, `wide-fanout`,
   `effect-in-effect-pass`, each with a fake-host test that triggers it
   (counted work; the hold on `asuka test`'s virtual clock) and one that
   doesn't.
6. **For agents.** `AGENTS.md` in `asuka new`, `asuka guide`, the test
   that it's current.
7. **The eval.** `eval/`, its tasks, a first run recorded in its
   README.
